# Kafka client telemetry with KIP-714 (phase 4)

[KIP-714](https://cwiki.apache.org/confluence/display/KAFKA/KIP-714%3A+Client+metrics+and+observability)
lets Kafka clients push their own metrics to the broker. The cluster operator decides which
clients send which metrics, without any change to the application code or configuration
(`enable.metrics.push` is `true` by default in recent Java clients).

The broker does not store these metrics. It hands them to a plugin. This demo provides a small
plugin that forwards them to the OpenTelemetry gateway.

```
kip714-demo (producer + consumer)          no OTel agent, no OTel SDK
      |  GetTelemetrySubscriptions / PushTelemetry   (Kafka protocol)
Kafka broker
      |  ClientTelemetryExporterProvider             (broker plugin API)
ClientOtlpMetricsReporter                         plugins/client-telemetry-reporter
      |  OTLP/gRPC
OTel gateway -> VictoriaMetrics -> Grafana "Kafka Client Telemetry (KIP-714)"
```

**Difference with application instrumentation (phase 3).** With the OpenTelemetry Java agent, the
application sends OTLP to a collector. With KIP-714, the client only talks Kafka protocol to the
broker. The broker plugin is the first component that sends OTLP. KIP-714 uses the OpenTelemetry
metrics data model, but it is not an OpenTelemetry SDK exporter.

## 1. Broker side

Three broker properties (set in `ansible/inventory.yml`, `kafka_broker_custom_properties`):

```properties
# Load the plugin. Keep any reporters you already have in this list.
metric.reporters=com.demo.kip714.ClientOtlpMetricsReporter
# Let the broker hand client metrics to the plugin.
confluent.telemetry.external.client.metrics.push.enabled=true
# Where the plugin sends OTLP.
client.telemetry.otlp.endpoint=otel-gateway:4317
```

The plugin JAR must be on the broker classpath. The lab image copies it to
`/usr/share/java/kafka/client-telemetry-reporter.jar` (see `docker/node.Dockerfile`).

The plugin implements `MetricsReporter` (so the broker loads it from `metric.reporters`) and
`ClientTelemetryExporterProvider` (the Kafka 4.x API that receives client payloads). For each payload it:

1. checks the content type (`OTLP` in Kafka 4.3);
2. adds resource attributes if the client did not send them: `client.id`, `client.instance.id`,
   `client.address`, `kafka.push.interval.ms`, `telemetry.source=kip714`;
3. sends an OTLP `ExportMetricsServiceRequest` to the gateway, from a separate thread with a
   bounded queue, so the broker request path is never blocked.

It also exposes its own counters through JMX. The broker JMX Exporter rules turn them into:

| Metric | Meaning |
|---|---|
| `kip714_reporter_payloads_received_total` | payloads handed to the plugin by the broker |
| `kip714_reporter_payloads_exported_total` | payloads sent to the gateway |
| `kip714_reporter_payloads_failed_total` | payloads that could not be parsed or sent |
| `kip714_reporter_payloads_dropped_total` | payloads discarded because the queue was full |

Plugin messages are written to the broker `server.log` (search for `KIP-714`).

> The plugin is **demo code**: plaintext gRPC, no retry, in-memory queue. Production use needs
> TLS, retry and backpressure decisions, and a support decision.

## 2. Which clients push: CLIENT_METRICS subscription

`scripts/configure-client-metrics.sh` creates a subscription that selects only the demo clients:

```bash
kafka-client-metrics --bootstrap-server broker1:9092 --alter --name kip714-demo \
  --metrics '*' --interval 10000 --match 'client_id=kip714-demo-.*'
```

- `--metrics '*'`: all client metrics. Use name prefixes to reduce the volume, for example
  `org.apache.kafka.producer.record,org.apache.kafka.consumer.fetch.manager`.
- `--interval 10000`: push every 10 s.
- `--match`: which clients. Other matchers are `client_software_name`, `client_instance_id`,
  `client_source_address` and others.

Other clients of the cluster are not affected. This is how KIP-714 can be enabled for selected
applications only.

## 3. Client side

`apps/kip714-demo` is a plain producer and consumer (Kafka Java client 4.3.0):

- `client.id` = `kip714-demo-producer` and `kip714-demo-consumer`, group `kip714-demo-group`;
- `enable.metrics.push=true` (explicit for readability; it is the default);
- at startup, it prints the `client.instance.id` of each client. This UUID is the key the broker
  uses for this client's telemetry, and it becomes the `client_instance_id` label:

```text
KIP-714 Producer:
  client.id = kip714-demo-producer
  client.instance.id = fGH-SveQS1ig7s-NQ7Zb_A
```

The consumer only gets its instance id after its first `poll()`, so the application reads it from
the consumer thread.

## 4. See and test it

```bash
./scripts/kip714-status.sh        # subscription, plugin counters, series per client_id
python3 scripts/extended-smoke.py # end-to-end test (also covers phase 3)
```

In VictoriaMetrics, the client metrics are named `org_apache_kafka_producer_*` and
`org_apache_kafka_consumer_*`:

```promql
org_apache_kafka_producer_record_send_rate{telemetry_source="kip714"}
org_apache_kafka_consumer_fetch_manager_records_lag_max{client_id="kip714-demo-consumer"}
```

Grafana dashboard: **Kafka Client Telemetry (KIP-714)**. It shows the plugin counters and the
producer and consumer metrics per `client_instance_id`.

A new `client_instance_id` appears each time the application restarts. Old series stop and
new ones start, which is expected.

## Version notes

- CP 8.3.x embeds Kafka 4.3.x. The plugin is compiled against `kafka-clients` 4.3.0 and uses the
  `ClientTelemetryExporterProvider` interface. The older `ClientTelemetry` receiver API is not used.
- KIP-1076 (applications adding their own metrics to the push) is available in this version.
  The demo does not use it, so that it only shows standard Kafka client metrics.
